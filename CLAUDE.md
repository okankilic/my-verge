# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Wishcrumbs (formerly Stashlog, Willa, Make It Real and Nowish, originally My Verge; the repo, app ID `com.okankilic.myverge` and the `my_verge_*` storage keys keep the old name on purpose, since renaming them would lose user data or the store identity) is a client-only React 19 + Vite + Tailwind CSS v4 single-page app, also shipped as iOS and Android apps through Capacitor 8: a mobile-first "bucket list and reminder journal" with a fixed set of verb categories (Go, Workout, Buy, Pay, Remember, Read, Watch, Cook, Taste, Learn and so on; users can't create their own). The UI calls each item a "plan" (one word for wishes, tasks and reminders); the code and this file still say "wish" and `BucketItem`. Likewise the `feed` tab is labelled Plans and the `milestones` tab Moments in the UI, while the code and this file call them the Journal and Memories (the stored field stays `hiddenInMemories`, so saved data keeps working). It was scaffolded in Google AI Studio (`metadata.json`, `.aistudio/`), and the package manager is Bun (`bun.lock`).

## Commands

```bash
bun install
bun run dev      # Vite dev server on port 3050, bound to 0.0.0.0
bun run build    # production build to dist/
bun run preview
bun run lint     # type-check only (tsc --noEmit); there is no ESLint
bun run cap:sync # build, then copy dist/ + plugins into android/ and ios/
bun run cap:android  # open the Android project in Android Studio
```

There's no test framework, so `lint` (type-checking) is the only automated check.

## Architecture

- **Single state owner:** `src/App.tsx` holds all application state: items, categories, the current tab, theme, default currency, the per-tab category picks, the search query, the Vault time range, and the open/closed flags for every sheet and drawer. There is no sort state: order comes from the `items` array (see Flows). It also defines every mutation handler (save, start, complete, reflection, keep/hide, steps, expenses, add photo/attachment, delete, reorder). Components in `src/components/` are presentational and receive data and callbacks as props. They have no context, store, or router. Tabs are switched through the `ViewTab` state (`feed | reminders | inprogress | vault | milestones`, labelled Plans, Horizon, Now, Vault, Moments). The default tab is `feed` (Journal). The Journal list is `JournalList`; the other tabs are `ReminderHorizonView`, `InProgressView`, `VaultView` and `MilestonesArchiveView`. Settings isn't a tab: `SettingsView` renders in a `Sheet` (`isSettingsOpen`) toggled by the gear in `TopNav`.
- **Item lifecycle:** `status` is `active | completed | archived`. An active item with `startedAt` set is "in progress": it appears on the Now tab and is excluded from the Journal feed and its category counts. `handleStart` sets `startedAt` (and switches to the Now tab and highlights the wish there). There is no Stop: a started wish never goes back to the Journal; it is finished or deleted, and completing an item clears it and opens `MilestoneSheet` for a reflection. A wish is in the Vault while its category's `keepInVault` is on (Read, Watch and Buy start on); that is managed only from Settings' "Show in Vault" toggles, which apply at once to every plan in the category, and there is no per-wish switch. The sheet starts unrated (0 stars), so closing it without tapping a star stores no rating (saving only a note writes `completionRating: 0`, which still reads as unrated). The sheet and `ItemDetailDrawer` have a "Hide in Moments" switch (`hiddenInMemories`, reset to shown on every finish; hidden wishes leave the Memories timeline and its counts but stay listed in a collapsed Hidden section at its bottom), and the drawer shows a finished wish's date, rating and reflection. The Vault (`isInVault` in `VaultView.tsx`) sums up active and finished wishes from the categories switched on in Settings (`keptCategoryIds`), as one per-category Summary (completed, in progress and awaiting counts, plus spent and budget per currency); picking a category (from the ribbon or a Summary row) also lists its Vault wishes under Done, In progress and Awaiting, and tapping one opens the drawer. Its time button (`TimeRangeFilter`, right-aligned with a down arrow, labelled with the selected range, e.g. "All time", with Clear to its left while one is set) opens a sheet of calendar ranges (`src/utils/timeRange.ts`: this/last week, month and year, weeks starting Monday, plus each earlier year that has Vault wishes). Ranges go by `vaultDate` (finished date for done wishes, otherwise created date). `vaultRange` lives in `App.tsx`, in memory only, and also narrows the ribbon counts. Starting, completing and deleting each ask first through `InlineConfirm` (`src/components/InlineConfirm.tsx`; `planConfirmCopy` holds the wording, `PlanConfirm` renders it), shown under the card's action row or at the top of the drawer footer; confirming acts at once with a plain toast and there is no Undo. Settings' Reset uses the same component in red. A finished wish can't be reopened: finished wishes have no ✓. A wish can have a checklist of steps (`BucketItem.steps`, `WishStep` with an optional `doneAt`), shown by `StepList` under "Along the way": added, ticked and removed in `ItemDetailDrawer` and in the form (local edits), with each removal confirmed inline in `StepList`, ticked on the Now card, counted as `2/4` (`StepCount`) on Journal rows and Memories cards, and matched by search. Finishing a wish leaves its steps as they are. A wish can also have a "Before you start" prep checklist (`BucketItem.prepSteps`, same `WishStep` shape, `StepList kind="prep"`), edited in the form and drawer (the drawer keeps it, still editable, once the wish is started or finished), counted on Journal rows until it's all ticked, and matched by search. It never blocks Start; the Start toast just says how many prep items are left. `updateSteps` and the step handlers in `App.tsx` take a `StepListKey` to pick the list. In-progress and finished wishes can also log expenses (`BucketItem.expenses`, `WishExpense` with an amount, optional note and `spentAt`): added through `ExpenseSheet` from the `$` button on the Now card, from `ExpenseList` in `ItemDetailDrawer`, or from `ExpenseList` in `MilestoneSheet` when a wish is finished, removed after an inline confirm in `ExpenseList`, and totalled (`src/utils/expenses.ts`) as "spent" on the Now card and against `budget.estimatedCost` in the drawer. Finished wishes keep theirs; `normalizeItems` drops malformed ones. Each wish has one currency (`BucketItem.currency`, an ISO code from `src/data/currencies.ts`) for its budget and expenses, picked in the form and formatted by `formatMoney` through `Intl.NumberFormat`. New wishes start with the Settings default (`my_verge_currency_v1`), and `stampCurrency` gives wishes without one the default on hydrate, so changing the default only affects new wishes. `normalizeItems` moves the old `budget.currency` symbol onto the wish as a code, and the Vault ledger totals each currency separately. Creating a wish from any tab but the Journal shows an "Added to your Plans" toast with an Open action. Deleting removes the wish's attachment blobs at once.
- **Journal order:** the Journal shows items in the order of the persisted `items` array, which the user sets in `JournalList` (`motion` `Reorder`) by pressing and holding an item for 2 seconds, then dragging it. Moving the finger before the press fires cancels it, so scrolling still works. `handleReorderJournal` in `App.tsx` reorders only the visible subset among the slots it already occupies, so items hidden by filters or search keep their places. New items are prepended, so they land at the top.
- **Search:** search is global. `searchedItems` in `App.tsx` feeds every tab. `SearchBar` (rendered under `TopNav`) is toggled from the floating Search button in `FloatingActions`, and closing it clears the query. `CategoryRibbon` is rendered above every tab, but each tab keeps its own pick (`categoryByTab`, in memory only), and `filteredItems` (search plus the current tab's category) feeds those tabs. The ribbon counts follow the current tab through `inTabScope`, and the ribbon only shows categories whose count is above zero, plus the selected one. Search matches the title, description, place name, author/creator, step and prep titles, and expense notes (not the city, link or reflection). Badges, notifications and Serendipity use the unfiltered `items`. Serendipity (`SerendipitySheet`, a random active wish) is switched off by `SHOW_SERENDIPITY = false` in `TopNav.tsx`, so it can't be reached today.
- **Navigation:** Search and New are floating round buttons (`FloatingActions`, `fixed`, `z-30`) stacked at the bottom-right on every width: above the dock on phones, in the corner from `md:`. They sit under sheets and toasts; from `sm:` toasts show at the bottom-left so they don't cover them. `BottomTabBar` is phone-only (`md:hidden`) and shows five tabs in a row (Plans, Horizon, Now, Moments, Vault, with the due-reminder badge on Horizon and an accent bar over the active one). `TopNav` holds the brand (which goes to the Journal), the desktop tab links (from `md:`, in the same order as the dock, with the due-reminder badge on Horizon), a Settings gear at the far right on every width (the only way to Settings; it toggles the Settings sheet) and a phone-frame preview toggle (`isMobileFrame`, web only, from `lg:`, in memory only; it narrows `<main>` to 420px). A spacer at the end of `<main>` keeps content clear of the bottom bar and the floating buttons.
- **Persistence:** never use `localStorage`/`sessionStorage`. `src/services/storage.ts` stores the versioned keys `my_verge_bucket_items_v1`, `my_verge_categories_v1`, `my_verge_theme_v1`, and `my_verge_currency_v1`. On the web they go in IndexedDB (DB `my_verge_data_v1`, store `kv`). On native each key is a `<key>.json` file in `Directory.Data` through `@capacitor/filesystem`, which the OS doesn't evict. The IndexedDB plumbing is shared with attachments in `src/services/idb.ts`. Loads are async: `App.tsx` starts empty, hydrates on mount, and renders a blank page until that finishes (or the Retry screen if reading failed). Saving, `syncNativeReminders`, and the reminder poll are all gated on `isHydrated`, so the empty initial state never overwrites stored data or cancels OS notifications. After hydration, `App.tsx` saves on every state change through `useEffect`. Saves are fire-and-forget and run in a queue per key. If storage is empty or holds an empty array, it is re-seeded from `src/data/initialData.ts` / `src/data/categories.ts` and the samples are saved at once. As a result, deleting every item brings the sample data back on the next load. A read error (IndexedDB failure, or on native a `readFile` error while `<key>.json` is still listed in `Directory.Data`) makes the load throw: `App.tsx` then shows a "Your journal didn't open this time" screen with Retry and never saves, so stored data is never overwritten. A value that reads but can't be understood (bad JSON, not a list) is first copied to `<key>_unreadable_<ms>` (the load fails if that copy can't be written), then the samples take over and a toast says a copy was kept. `loadCategories` runs categories through `normalizeCategories`, and `loadBucketItems` runs items through `normalizeItems`; the Migrations flow below lists every rule. If you change the shape of `BucketItem` or `CategoryDefinition` (`src/types/index.ts`), add a migration there or bump the key. Reset-to-sample, theme picker, and chime test live in `SettingsView`. Video/PDF attachments are stored separately (`src/services/attachments.ts`). On native they are files at `attachments/<id>/<name>` in `Directory.Data`, written in 3 MiB base64 chunks. On the web they go in IndexedDB (DB `my_verge_attachments_v1`). Items keep only `AttachmentMeta`. Theme and currency are stored as raw strings (`light`, `USD`), so their `.json` files on native aren't actually JSON.
- **Photos and attachments:** `src/components/ItemActions.tsx` owns the Camera and Attach buttons, which appear on Now and Memories cards (the drawer, Journal rows and Horizon cards have no add buttons). Images are downscaled to JPEG data URLs (`src/utils/imageResize.ts`, 1024px longest side, quality 0.72) and stored in `BucketItem.photos`; `photos[0]` is the cover. `ItemMediaStrip` shows every photo (cover included, newest first) plus attachments on the Now card, and the photos after the cover plus attachments on Memories cards and in `ItemDetailDrawer`. There is no UI to remove a photo or attachment; blobs go only when their wish is deleted or a reset orphans them. The sample data uses stable paths under `public/presets/` (`src/data/presetPhotos.ts`); never move them, since items store the URL, and `normalizeItems` remaps the old dev-only `/src/assets/images/...` paths. Photo captions are stored in `photoNotes`, keyed by `photoKey()` (`src/utils/photoKey.ts`); attachment captions are stored in `AttachmentMeta.note`. Videos and PDFs up to `MAX_ATTACHMENT_BYTES` (100 MB) are saved through `saveAttachment` (filesystem on native, IndexedDB on web). `MediaNoteSheet` asks for a caption of up to `MEDIA_NOTE_MAX_LENGTH` (100) characters. Phones use the native `<input capture>`, while desktops (non-coarse pointer) use `WebcamCaptureSheet`. Deleting an item also deletes its attachment blobs.
- **Reminders:** `src/services/notifications.ts` checks for due items (`getDueReminderItems`). It also plays a chime synthesized with the Web Audio API (no audio assets) and sends browser `Notification`s on the web. `App.tsx` polls every 30 seconds, and also checks at once whenever `items` changes (the effect depends on `items`). For the first fresh due item it shows an in-app reminder banner (an inline strip in `<main>`, not a `DialogHost` toast, with a dismiss X), plays the chime and sends a browser notification. Each occurrence alerts only once: the poll stamps `reminder.lastNotifiedAt` on every fresh due item (`getUnnotifiedDueItems`), including ones after the first that got no banner. All reminder timing goes through `reminderTime` / `reminderDueAt` / `reminderNextAt` / `isReminderDue` in `notifications.ts`. A one-off reminder stays due until it is completed. There is no snooze (it was removed; `normalizeItems` drops a stored `reminder.snoozedUntil`). A recurring one is due only on the day of its latest occurrence and then rolls forward to its next one. On native, `src/services/reminderScheduler.ts` (`syncNativeReminders`) re-schedules OS notifications through `@capacitor/local-notifications` every time `items` changes, and when alerts are enabled from Settings or Horizon. That lets reminders fire while the app is closed. Syncs run one at a time, and calls made during one collapse into a single follow-up run with the latest items. Date-only reminders fire at 9:00 local time; the form only writes `datetime-local` values, so this applies to sample, legacy and imported data. Tapping a notification opens its item's drawer over the current tab (the tab doesn't change).
- **Sharing:** the Share button in `ItemDetailDrawer` calls `shareItem` (`src/services/shareOut.ts`). It sends the wish's text, link and cover through `@capacitor/share` on native, or `navigator.share` on the web, and copies the text to the clipboard when the browser has no share sheet. Receiving is native only. The app's own `ShareInbox` plugin keeps shares waiting until `getPending` takes them and fires `shareReceived` when one arrives. `src/services/shareInbox.ts` turns each share into a draft (`toDraft`), and `App.tsx` opens `ItemFormDrawer` with it as `draft` (queued while the form is open). On Android, `ShareInboxPlugin.java` handles `ACTION_SEND` (text and `image/*`) through `handleOnNewIntent`, consumes the intent, and only reads images from other apps' `content://` providers. It is registered in `MainActivity`. On iOS, the `ShareExtension` target (`ios/App/ShareExtension/`) writes each share to the App Group `group.com.okankilic.myverge` as `ShareInbox/<id>/share.json` plus `image.jpg`. Extensions can't open their app, so `ShareInboxPlugin.swift` picks shares up when the app becomes active, and it is registered in `MainViewController`. The Apple Developer portal needs the `com.okankilic.myverge.ShareExtension` ID and the App Group enabled on both IDs, and Codemagic has to fetch a profile for the extension too (`codemagic.yaml` currently lists only `bundle_identifier: com.okankilic.myverge` under `ios_signing`).
- **Native (Capacitor):**
  - `capacitor.config.ts` sets the app ID `com.okankilic.myverge` (permanent), and `webDir` is `dist`.
  - `android/` and `ios/` are committed. Edit their manifests and plists directly. After any web change, run `cap:sync`.
  - `src/services/platform.ts` exports `isNative`. Web-only APIs must branch on it:
    - Blob URLs and `window.open`: on native, `openAttachment` hands the stored file to the system viewer in place.
    - `target="_blank"` links: use `externalLinkProps(url)` / `openExternal(url)`.
    - `new Notification`: replaced by the scheduler above on native.
  - `applyNativeTheme` keeps the status bar in sync with the theme.
  - Icons and splash screens are generated from `assets/*.png` by `@capacitor/assets`. Those PNGs, `public/favicon.svg` and `public/apple-touch-icon.png` are rendered from the brand mark (four crumbs growing along a rising trail, the last one Terracotta) in `assets/brand/render.mjs`. To regenerate everything, run `node assets/brand/render.mjs`, then `node node_modules/@capacitor/assets/bin/capacitor-assets generate --android --ios`. Afterwards, revert the generator's line-ending-only changes to XML/JSON files. The TopNav mark is an inline copy of the same SVG.
  - iOS builds run on Codemagic (`codemagic.yaml`), since there is no local Mac. Android is built locally in Android Studio.
- **Category labels:** a category has no `name`; its `verb` is the label. The built-in categories are the 18 verbs in `DEFAULT_CATEGORIES` (`src/data/categories.ts`), each with the lowercase verb as its id. There is no way to create a category. `normalizeCategories` adds any missing verb on load and sorts the list into the default order, keeping categories that older builds let users create (ids `custom-*`) so their items still resolve. Verbs retired from older builds (Explore, Grow, Do, Practice, Make, Build, Write, Collect) are listed in `MERGED_VERBS`: `normalizeCategories` drops them, and `normalizeItems` moves their wishes to the verb they merged into.
- **Category icons:** each verb has a fixed Lucide icon set in `DEFAULT_CATEGORIES` (`CATEGORY_VERB_ICONS` is derived from it), so users don't pick one. A category stores the icon as a string name (`CategoryDefinition.icon`), and `normalizeCategories` resets it to its verb's icon on load. `src/utils/categoryIcons.tsx` maps those names to components, so adding a verb means adding an entry to `DEFAULT_CATEGORIES` and its icon to that map.
- **Styling:** Tailwind v4 is loaded through `@tailwindcss/vite` with `@import "tailwindcss"` in `src/index.css`, so there is no `tailwind.config`. The look is warm modern minimalism from `branding.md`: Oat and Cocoa neutrals, one Terracotta accent and a Forest dark theme. Colors are `@theme` tokens in `src/index.css` (`ink`, `page`, `paper`, `card`, `paper-deep`, `warm`, `sage-tint`, `sage-deep`, `link`, `accent`, `alert`, `positive`, `danger`, `switch-on`), used as `bg-card`, `text-ink`, `border-ink/15`, and so on. Dark mode overrides those tokens: it follows `prefers-color-scheme` unless `data-theme="light"` is set on `<html>`, and `data-theme="dark"` forces it. Use the tokens for surfaces and text. Use `accent` (`text-accent`, `fill-accent`, `bg-accent/15`) for brand highlights such as stars, icon highlights and the wordmark hover. `accent` and `link` are a deeper Terracotta than the brand `#D98F6B`, which is too light for text and stays for the logo. Use `text-alert`, `text-positive` and `text-danger` for due, done or spent, and delete text and icons; raw `#C05621` and `#4A6B56` remain only as fills behind white text. Keep raw hex for fixed accents only, and check those in dark mode. Category colors go through `categoryColor` (`src/utils/categoryIcons.tsx`), which blends them toward `ink` by `--category-lift` (0% light, 55% dark) at render time, so stored categories need no migration. The saved theme is applied by a `useEffect` once hydration finishes, so it lands right after the first hydrated render (a one-frame flash is possible). There is no pre-paint script, because storage can't be read synchronously. Fonts are bundled through `@fontsource` imports in `src/main.tsx` (no Google Fonts, so the app works offline): Plus Jakarta Sans for display headings (`.font-serif-journal`, a legacy class name kept to avoid churn), Inter for body text, and JetBrains Mono (`.font-mono-journal`). Animation uses `motion`, and completions trigger `canvas-confetti`.
- **Sheets and toasts:** every overlay is `src/components/Sheet.tsx`, a bottom sheet on phones and a right-side drawer from `sm:` (backdrop tap and Escape close it, Escape is ignored while typing in a field and only reaches the top sheet, and `stacked` raises one that opens over another). `Sheet` is not a portal: it renders where it is used, so a sheet opened from inside another sheet's `<form>` is nested inside that form in the React tree. `src/services/dialogs.ts` exposes `notify(message, tone, { action, durationMs })` and `notifyUndo(message, onUndo)` (unused today: actions confirm first instead). There is no confirm API; confirms are inline (`InlineConfirm`). These are rendered as toasts by `src/components/DialogHost.tsx`, which is mounted once in `App.tsx`. This is the one deliberate exception to the single-state-owner rule, so services and deep components can report without prop drilling. Settings' reset confirms inline in the sheet with the same `InlineConfirm`.
- **Path alias:** `@/*` resolves to the repo root, not `src/`.

## Flows

Step-by-step walkthroughs of what happens for each user action and background process. Handlers live in `src/App.tsx` unless another file is named.

### Boot and saving
1. `main.tsx` imports the fonts and `index.css` and renders `<App/>` (no StrictMode). State starts empty, and the app renders a blank `bg-page` div until hydration ends. If a load throws, `loadFailed` shows the Retry screen instead, and Retry bumps `loadAttempt` to run the loads again.
2. On mount, `loadBucketItems`, `loadCategories`, `loadTheme` and `loadDefaultCurrency` run in parallel. Items go through `stampCurrency` with the loaded default, then everything is set and `isHydrated` turns true.
3. The hydrated effects then run once and on every later change: items are saved and `syncNativeReminders(items)` runs; categories, theme (`data-theme` on `<html>`, `saveTheme`, `applyNativeTheme`) and currency are saved. This first save also writes any migrations back to storage.
4. Each save goes through `queueWrite` in `storage.ts`, one promise chain per key, writing the whole value. Failures are only logged to the console.
5. On mount, App also registers `onReminderTapped` and `onSharedContent` (both native only).

### Migrations (`normalizeItems`, `normalizeCategories` in `storage.ts`)
Run on load, never on the seeded samples. Both drop entries that aren't objects first, and `normalizeItems` turns a `photos` value that isn't a list of strings into one, so a single damaged entry can't make loading fail.
- **Items, in order:** drop `subCategory` and the retired per-wish `keptInVault`; remap old `/src/assets/images/...` preset paths to `/presets/...` (moving their `photoNotes` captions to the new `photoKey`); move wishes in retired categories to their merged verb (`MERGED_VERBS`); drop a stored `reminder.snoozedUntil` (snooze was removed); move the old `budget.currency` onto `item.currency` (valid codes kept, `$ € £ ₺ ¥` mapped to USD/EUR/GBP/TRY/JPY, anything else becomes the default) and drop it from `budget`; clear an invalid `item.currency` so `stampCurrency` fills it; a wish with a `targetDate` gets `priority: 'until'`; keep only steps/prep with a string `id` and a non-blank `title`, and expenses with a string `id`, a finite `amount` above 0 and a string `spentAt` (empty lists become `undefined`). Reminders, attachments, status and dates pass through unchecked (a reminder whose date can't be read never comes due and gets no OS alert).
- **Categories:** drop `name` and `defaultSubCategories`; take the label from `verb` or the legacy `name`, strip a leading "Want to ", trim and capitalize; reset `icon` to the verb's icon (unknown verbs keep theirs); fill a missing `keepInVault` from `KEEP_IN_VAULT_VERBS` (Read, Watch, Buy); drop categories whose id is a merged verb; append any missing default verb; sort into `DEFAULT_CATEGORIES` order with unknown (`custom-*`) ones last. `accentColor` and `tagline` are kept as stored.

### Creating a wish
1. The floating `+` in `FloatingActions` or New in the empty Journal all run `setEditingItem(null)` and open `ItemFormDrawer`.
2. The form starts in the current tab's category pick (Go when it's All) and the default currency. Fields: category grid, title (required, placeholder follows the category), author and format (Read and Watch only), notes, link, When (`priority`: Urgent, This month, This year, Someday or Until; picking Until shows the Target date field) and its target date (both display-only, shown in the drawer header and body), Where (place and city), "Before you start" prep list, "Along the way" steps, reminder (checkbox, `datetime-local`, recurrence), currency, target and saved amounts.
3. Save calls `handleSubmit`, which returns silently on an empty title. A step or prep item still typed in its add field is included. The place is kept only with a name, the budget only with a target, the author/format only when one is filled, the reminder only when both the checkbox and the date are set, and the target date only with Until (Until without a date saves as This year).
4. `handleSaveItem` builds the item with id `verge-<ms>-<rand>`, `status: 'active'` and fallbacks (Go, "Untitled Wish", `this_year`, the default currency) and prepends it to `items`.
5. From any tab but the Journal it shows "Added to your Plans!" with an Open action that switches to the Journal.

### Shared drafts (native)
1. `onSharedContent` (`shareInbox.ts`) drains `getPending()` at mount and again on each `shareReceived` event, converting each share with `toDraft`: the link comes from the payload URL or the first `http(s)` match in the text (removed from the text); the title is the subject, else the first line, else the link's host; the rest becomes the description; titles over 80 characters are cut and kept in full in the description; a shared image becomes a 1024px JPEG data URL in `photos[0]`.
2. Drafts queue in `queuedShares`. Once hydrated and while the form is closed, the next draft opens in `ItemFormDrawer` as `draft`, and its image becomes the cover. Saving follows "Creating a wish"; closing the form lets the next draft open.

### Editing a wish
1. Edit in the drawer footer opens the form with `editingItem` (Memories' Edit opens `MilestoneSheet` instead).
2. Save merges `{...item, ...itemData}`. The form sets every field it edits, writing `undefined` for blank ones, so emptying the place, budget, author/format, target date, link or reminder clears it. `mediaMeta.progress`, which the form doesn't edit, is kept.
3. The form has no photo fields and leaves `photos` untouched; photos are added from the Now card.
4. If the reminder's date and recurrence are unchanged, `lastNotifiedAt` carries over; otherwise it resets so the new schedule alerts.
5. Changing a wish's currency relabels its budget and expenses without converting them, so when the wish has a target, a saved amount or expenses the form asks first ("Switch to EUR?" under the Budget header).
6. Closing the form (backdrop, Escape, X, Cancel) with unsaved changes shows a Discard / Keep confirm at the top of its footer. Changes are found by comparing a snapshot of every field (step and prep drafts included) with one taken right after the form was filled.

### Starting
1. ▶ in `ItemActions` (Journal rows and Horizon cards of unstarted wishes; Now cards have none) or Start in the drawer (unstarted wishes only) calls `handleStart`, which ignores wishes already started or finished. There is no Stop anywhere.
2. ▶ first opens the inline Start confirm (with how many prep items are left); confirming sets `startedAt`, patches the open drawer copy, and shows a toast saying the wish is on Now and how many prep items are left; prep never blocks it. The wish moves from the Journal to Now for good.
3. Starting also switches to the Now tab, clears Now's category pick if it would hide the wish, closes the drawer if it shows that wish, and sets `focusedNowId`: `InProgressView` scrolls the card into view, focuses it and rings it in `accent` for 1.6 seconds, then clears it.

### Finishing and the MilestoneSheet
1. ✓ in `ItemActions` or the drawer (shown only on unfinished wishes) opens an inline `InlineConfirm` ("Mark "<title>" as done?", Cancel / Done; the drawer resets it when it shows another wish), and Done calls `handleToggleComplete`, which ignores finished wishes. It snapshots the fields it is about to change, sets `status: 'completed'`, `completedAt`, `hiddenInMemories: false`, clears `startedAt`, fires confetti and the chime, closes the drawer, and opens `MilestoneSheet` (keyed by item id).
2. There is no Undo: the ✓ confirm is the safeguard.
3. In the sheet, the 5 stars and the note are local and saved by `handleSaveReflection` on every way out (Close, backdrop, Escape) when they changed. The expense list and the Hide in Moments switch (`handleToggleHiddenInMemories`, no Undo) apply at once.
4. Memories' Edit reopens the same sheet to change the reflection, rating, expenses and Hide switch, with no confetti or toast.
5. There is no reopen: a finished wish stays finished.

### Deleting
1. The trash button in `ItemActions` or the drawer opens the inline Delete confirm, then calls `handleDeleteItem`, which removes the wish, clears the reminder banner and drawer if they show it, deletes its attachment blobs at once, and shows `"<title>" is gone.`
2. Nothing is kept for Undo: the wish and its attachment files are gone once confirmed.

### Steps and prep
1. `updateSteps(id, change, list)` applies a change to `steps` or `prepSteps` (`StepListKey`) on both `items` and the drawer copy through functional updates, storing an empty list as `undefined`.
2. `handleToggleStep` sets or clears `doneAt` (Now card steps, drawer), `handleAddStep` adds a `step-<ms>-<rand>` step (drawer), and `handleRemoveStep` removes one after `StepList`'s inline confirm (drawer; the form's removal confirms the same way).
3. Prep is shown in the drawer while the wish is unstarted, or whenever it has prep. Journal rows show the prep count until it's all ticked, and the step count `2/4`.

### Expenses
1. Add from the `$` button on a Now or Memories card (`ExpenseSheet`), from `ExpenseList` in the drawer (Add appears only for started or finished wishes; removal works any time) or in `MilestoneSheet`.
2. `ExpenseSheet` takes an amount (`parseAmount`: above 0, 2 decimals, comma accepted as the decimal mark) and an optional note of up to 60 characters. `handleAddExpense` appends `newExpense(...)` and shows "Logged ..." (no Undo); `handleRemoveExpense` removes one after `ExpenseList`'s inline confirm.
3. `src/utils/expenses.ts` totals them as "spent" on the Now card and against the budget target in the drawer, formatted in the wish's currency by `formatMoney`.

### Photos and attachments
1. On a Now or Memories card, Camera opens a hidden `<input accept="image/*,video/*" capture="environment">` on touch devices (or without `getUserMedia`), otherwise `WebcamCaptureSheet` (photos only; Capture, then Retake or Use; Browse switches to the file picker). Attach opens a multi-file picker for images, videos and PDFs.
2. `ItemActions` rejects other types and files over `MAX_ATTACHMENT_BYTES` with a toast, then queues the rest. `MediaNoteSheet` shows each one ("n of N") with a preview and an optional caption (Skip or Save; closing counts as Skip). The queue lives in that card's `ItemActions`.
3. Images are downscaled and passed to `handleAddPhoto`, which appends to `photos` and stores the caption in `photoNotes`. Videos and PDFs go to `handleAddAttachment`, which awaits `saveAttachment` under id `att-<ms>-<rand>` and then appends `AttachmentMeta`; a failure shows "Couldn't add ...".
4. Tapping an attachment chip calls `openAttachment`: the system viewer on native, a new tab with a Blob URL on the web.

### Reminders
1. **Timing (`notifications.ts`):** `reminderTime` reads `YYYY-MM-DD` as 09:00 local and anything else as a local date-time. Recurring occurrences add days, weeks, months or years to the base, clamping month ends (Jan 31 recurs on Feb 28). `reminderDueAt` is the latest occurrence (null before the first one). `isReminderDue` holds a one-off due from then on, and a recurring one only on the calendar day it fell due. `reminderNextAt` gives the next alert time for the Horizon.
2. **Poll:** once hydrated, `checkReminders` runs at once, every 30 seconds, and on every `items` change. It takes `getUnnotifiedDueItems` (active, due, `lastNotifiedAt` older than the due time), shows the banner for the first one, plays the chime, calls `sendBrowserNotification` (web only, needs permission), and stamps `lastNotifiedAt` on all of them.
3. **Banner:** tap opens the drawer, X dismisses it.
4. **Native:** `syncNativeReminders` queues a sync (one runs at a time; calls during a run collapse into one more run with the latest items). Each sync plans alerts for every active wish with a readable reminder date, then cancels every pending OS notification and schedules the plan (`stableIntId(item.id)` for a wish's next alert, `stableIntId("<id>#<n>")` for later ones, `extra.itemId` on all):
   - a repeat whose first occurrence has passed uses a repeating `on` schedule (daily, weekly, monthly on days 1-28, yearly except Feb 29);
   - repeats that haven't started yet, and monthly/yearly ones on days the OS would skip in some months, get their next 8 occurrences (`ONE_OFF_AHEAD`) as one-offs from `upcomingOccurrences`, which clamps month ends like the in-app checks; the next sync tops them up;
   - a one-off fires only while it's in the future.

   Each wish's next alert is kept first, then extra one-offs soonest first, up to 64 in all (the iOS limit). If the OS rejects the batch, each alert is scheduled on its own so one bad alert can't leave the rest unscheduled. A tap sets `tappedItemId`, which opens that wish's drawer once hydrated.

### Journal reorder
1. In `JournalList`, pressing a row for 2 seconds (`LONG_PRESS_MS`) lifts it (scale, ring, 30ms vibration, page scroll locked); moving more than 8px first cancels. A click right after the press is swallowed.
2. The row is dragged with `motion` `Reorder` against local order, and on release `handleReorderJournal` writes the visible ids back into the array slots they already held.

### Search, category filter and counts
1. The search toggle opens `SearchBar` under `TopNav` (autofocus, Escape closes); closing clears the query. `searchedItems` applies it to every tab.
2. Each tab keeps its own ribbon pick in `categoryByTab` (in memory; reset only by reset). `filteredItems` is `searchedItems` narrowed by that pick.
3. `inTabScope` decides what each tab counts and lists: Journal = active and not started; Now = started; Horizon = active with a reminder date or an Until target date (`targetDateTime` in `src/utils/targetDate.ts`) and, when a range is picked, a `horizonTime` inside `horizonRange`; Vault = `isInVault` and inside `vaultRange`; Memories = finished and not hidden.
4. Orders: Journal follows the `items` array; Now is most recently started first; Horizon puts due ones first, then by next alert time (or target date for wishes with no reminder); Memories goes by finish date, newest first.

### Horizon
0. A time filter (`TimeRangeFilter`, shared with the Vault: a right-aligned button showing the picked range with a down arrow, Clear to its left) sits at the top. Its sheet offers `HORIZON_RANGES` (All time, Today, This week, This month, In three months, In six months, This year; the month spans run from the start of today to the same day 3 or 6 months ahead, month ends clamped). Plans match by `horizonTime` (`src/utils/targetDate.ts`): now while due (so due plans show in every range), else the next alert, else the Until date. `horizonRange` lives in `App.tsx` in memory only, narrows `horizonItems` and the ribbon counts, and resets to All time on Reset. With a range that hides everything, the empty state says "<range> is all clear".
1. While notification permission hasn't been asked, a banner offers Enable (`onNotificationsEnabled` then re-syncs native reminders); if refused, a note points to system settings.
2. A timeline lists "Due (n)" first, then upcoming reminders grouped as Today, Tomorrow or a date, each showing its time, recurrence and "until <date>" when it has a target date, and the `ItemActions` row. A wish with an Until date and no readable reminder sits on its target day labelled "Until" (passed targets stay in date order, with no Due styling); each wish appears once. The badge counts due reminders only. With none, it shows "All clear for now".

### Vault
1. `VaultView` keeps `isInVault` wishes: active and finished wishes whose category has `keepInVault` on (Settings' "Show in Vault"). Archived wishes never show.
2. The page is only the Time filter and a Summary card (or the empty state): one row per category with Vault plans (`summarizeByCategory` in `src/utils/vaultSummary.ts`, so it follows the range, search and category pick), counting completed, in progress and awaiting, with Spent (expenses) and Budget (targets) totals per currency. Summary rows are buttons that pick their category (`onSelectCategory`, the same pick as the ribbon). With one category picked, its Vault plans are listed below in Done (newest finish first), In progress (newest start first) and Awaiting (Journal order) groups, each hidden when empty and grouped by `planStatus` (the test the Summary counts with). Each row shows the title and a mono line (finish date, "Since <date>" or the budget, plus spent) and opens the drawer. There are no cards, shelves or action buttons.
3. The time button, which shows the selected range at the top right with a down arrow, opens a sheet of ranges (`VAULT_RANGES`: All time, this/last week, month and year, then earlier years with Vault wishes from `earlierYears`). Picking one sets `vaultRange` and closes it; Clear goes back to All time. `isInRange` compares `vaultDate` (finish date for done wishes, otherwise created date).

### Memories
1. Finished wishes that aren't hidden form a timeline grouped by month (newest first, "Undated" last). Each card shows the category, step count, stars, title, reflection (or description), cover, and the other photos and attachments (`ItemMediaStrip`), then the shared `ItemActions` row like a Now card: Camera, Attach, $, Edit (opens `MilestoneSheet`) and Delete.
2. Hidden wishes sit in a collapsed Hidden section at the bottom (Show/Close); each row opens the drawer, where Hide in Moments can be switched off.

### Detail drawer
Tapping a Journal row, Horizon or Now card, banner, or hidden Memories row opens `ItemDetailDrawer` with `viewingItem`. Top to bottom: cover, title and author, description, media strip, prep, steps, expenses, "In progress since", target date, place (Maps), budget progress, link, reminder status, and for finished wishes the memory card plus the Hide in Moments switch. The footer has Edit, Share (`shareItem`), Delete, Start (only before a wish is started) and ✓ (hidden when finished).

### Settings
The gear in `TopNav` toggles a `Sheet` holding `SettingsView` over the current tab (`isSettingsOpen`, in memory only). It closes with its X, the backdrop or Escape, and a tap on the gear on phones lands on the backdrop. In order: theme (Light, Dark, System); default currency; "Show in Vault" toggles per category (`onCategoriesChange`), the only place the Vault's contents are managed; reminder alerts status and Enable; chime Test; Reset.
- **Reset:** an inline confirm, then `deleteOrphanedBlobs` (attachment blobs the current items reference but the samples don't) and `onReloadData` with `INITIAL_ITEMS` and `DEFAULT_CATEGORIES` (which also resets the keep defaults); `onReloadData` stamps the currency, replaces items and categories, and clears the category picks, the Vault and Horizon time ranges and the banner.

### Sharing out
`shareItem` builds the text ("Done with Wishcrumbs: <title> ★★★" plus the reflection for finished wishes, otherwise the title and description). On native it writes the cover to the cache and calls `Share.share` with title, text, link and file. On the web it uses `navigator.share` (with the cover file when `canShare` allows, retrying without it on `NotAllowedError`), or copies the text and link to the clipboard when there's no share sheet. Cancels are ignored; other errors show "Couldn't share".

### Receiving shares (native)
- **Android:** `MainActivity` (`singleTask`) accepts `ACTION_SEND` for `text/plain` and `image/*`. `ShareInboxPlugin.handleOnNewIntent` skips intents relaunched from history, reads `EXTRA_TEXT` and `EXTRA_SUBJECT`, and for images reads `EXTRA_STREAM` only from another app's `content://` provider (up to 20 MB, base64). It replaces the intent with `ACTION_MAIN` so it isn't handled twice, keeps the share in memory, and fires `shareReceived`; a cold start relies on the JS drain instead.
- **iOS:** the `ShareExtension` takes up to one URL, text and one image (downscaled to 1600px JPEG), writes `share.json` and `image.jpg` into a `.staging-*` folder in the App Group, then moves it to `ShareInbox/<ms>-<uuid>` and shows a confirmation that closes itself. `ShareInboxPlugin.swift` fires `shareReceived` when the app becomes active, and `getPending` returns the folders oldest first and deletes them.

### Building and releasing
- **Web changes to native:** `bun run cap:sync` (`vite build`, then `cap sync`).
- **Android:** `bun run cap:android`, then build in Android Studio. The version (`versionCode 1`) is set by hand in `android/app/build.gradle`.
- **iOS (Codemagic `ios-testflight`, started by hand):** install Bun and dependencies, `bun run build`, `npx cap sync ios`, `xcode-project use-profiles`, set the build number to the latest TestFlight build plus 1 (needs `APP_STORE_APPLE_ID`, still a placeholder), `xcode-project build-ipa`, then publish to TestFlight.

## Conventions

- **Brand.** `branding.md` is the brand source for name, voice, palette and logo. These conventions win where they differ: its "Let's make it happen" breaks the no-"let's" rule and "Add a crumb" breaks one-word buttons. The UI still says "plans", not "crumbs".
- **This is a mobile application.**
  - Design and verify at phone width (~390px) first; desktop is a secondary layout.
  - Touch targets are at least 44px.
  - Never rely on hover for meaning or actions.
  - Keep content clear of the fixed bottom tab bar and safe-area insets (`viewport-fit=cover` is set; `TopNav` pads by `safe-area-inset-top`).
- **No modals.** Never build a centered or blocking modal dialog. Overlays go through `Sheet` (bottom sheet on phones, side drawer from `sm:`). There are no blocking confirmations either: actions that change a plan (start, finish, delete, removing a step or expense, discarding form edits, switching a plan's currency when it has amounts) confirm inline in the page through `InlineConfirm`, then act at once with no Undo toast.
- **One-word buttons.** A button's visible label is a single word (icons and compact tokens like `+1d` are fine). Put any longer description in `aria-label`/`title`, or in nearby text.
- **Positive, encouraging copy.** All user-facing text (toasts, empty states, errors, hints, notifications, confirms) is warm, positive and direct. Speak to "you" and avoid "we" and "let's". Frame empty states as invitations ("Ready when you are", "All clear for now") rather than absences ("Nothing in progress"). Errors say what happened and offer a next step ("Couldn't add "x". Try again?") instead of "Failed" or "Invalid". Keep it short, and avoid formal or grandiose wording.
- **Empty states.** Every tab's empty state is `EmptyState` (`src/components/EmptyState.tsx`): icon, title, hint, and, while search or the tab's category pick hides plans (`clearFilters` in `App.tsx`), a filter hint plus a Clear button. The Journal adds New.
- **Wording.** Keep one vocabulary on every tab: finishing is "Done" (✓ is labelled "Mark as done", Vault groups and counts say "done"; never "accomplished", "completed" or "finished"); items are "plans"; media is "photo, video or PDF" (not "image"); Start's title is "Start — move to Now". Headings, labels and titles are in sentence case ("Reminder chime", not "Reminder Chime"). Write "e.g. " (no comma), "…" (not "..."), and lists without an Oxford comma.
- **No native browser dialogs.** Never use `window.alert`, `window.confirm`, or `window.prompt`. Use `notify` from `src/services/dialogs.ts` and `InlineConfirm` instead.

## Environment notes

- `.env.example` declares `GEMINI_API_KEY` and `APP_URL`, which AI Studio injects. Nothing reads them yet, and the app makes no server or AI calls. The unused `@google/genai`, `express`, and `dotenv` dependencies were removed.
- `vite.config.ts` turns off HMR and file watching when `DISABLE_HMR=true`; AI Studio sets this. The comment there says not to modify it.

## Known gaps

- `bun` may not be on the PATH. `npx bun@1.2.23 <cmd>` works without installing anything globally. In the Windows bash shell, run the Capacitor CLI as `node node_modules/@capacitor/cli/bin/capacitor`.
- On the web, all data (including attachments) lives in IndexedDB, and the browser can evict it.
- Data saved in localStorage by older builds is not migrated. Those installs start over from the sample data.

## Future plans

- **Suggest a new item using AI.** Not built yet. `GEMINI_API_KEY` is declared but unused. Calling Gemini from a client app would expose the key, so this needs a backend.
- **Suggest cooking recipes and travel itineraries using AI and what other people do.** Not built yet. The goal is to suggest a recipe for a Cook wish and a travel itinerary (stops, days, things to book and pack) for a Go wish. Suggestions would come from an AI model and from what other people did with similar wishes, such as the recipes cooked most often or the trips taken to the same city. Today the app has no backend, no accounts and no shared data. Every wish stays on the device (`src/services/storage.ts`), and Gemini can't be called from the client without exposing the key (see "Suggest a new item using AI"). This needs a server that holds the key and collects other people's activity, opt-in and anonymised. A suggestion would open as a draft in `ItemFormDrawer`, the way a shared draft from `toDraft` does. A travel itinerary would fill `prepSteps` and `steps`. A recipe needs the recipe fields planned under "Predefined, shareable recipes".
- **Read text from photos with OCR.** Not built yet. The goal is to read the line items on an invoice and sentences from a book page.
- **Track a product's price and notify.** Not built yet. The goal is to follow a wish's product price on sources the user picks (store pages or price feeds) and send a reminder when it drops or hits a target. The app has no backend, and fetching store pages from the client runs into CORS, so the checks need a server or scheduled job that pushes alerts to the native app.
- **Predefined prep checklists by category.** Not built yet. Each category could offer ready-made "Before you start" lists to pick from, filling `prepSteps` in the form. For example, Go could offer By car, By flight, In country and Out of country. The templates would live with the categories in `src/data/categories.ts`.
- **Recipes with a video for each step.** Not built yet. The goal is to store a recipe on a Cook wish, with each step carrying its own video. Today a `WishStep` only has an id, a title and `doneAt`, and videos attach to the whole wish (`AttachmentMeta` in `BucketItem.attachments`), so steps would need their own media, stored through `saveAttachment` like other videos and deleted with the wish.
- **Predefined, shareable recipes.** Not built yet. The goal is to ship ready-made cooking recipes that users can pick from when adding a Cook wish, and to let users share a recipe (a predefined one or their own) with others. Today a Cook wish has no recipe fields (only a title, notes and steps), sharing out (`shareItem` in `src/services/shareOut.ts`) sends just the text, link and cover, and a received share (`toDraft` in `src/services/shareInbox.ts`) becomes only a title and description, so a shared recipe needs a format that carries its ingredients and steps both ways. The predefined recipes could live with the other built-in data in `src/data/`, like the planned prep checklist templates.
- **Integration with hotel applications.** Not built yet. The goal is to link a Go wish with hotel booking apps and sites: search stays for the wish's place and dates, and bring a booking's hotel, dates and confirmation back onto the wish (place, target date, reminder, expenses). Booking APIs need partner keys that can't ship in a client app, so this needs a backend. A lighter first step could be receiving booking confirmations through the existing share inbox (`toDraft` in `src/services/shareInbox.ts`).
- **Siri voice control.** Not built yet. The goal is to add, start and finish wishes by voice through Siri. This needs native iOS code (App Intents in Swift), handed to the web app through a Capacitor plugin the way `ShareInboxPlugin.swift` hands over shares, plus the Siri capability on the `com.okankilic.myverge` ID and in the Codemagic signing setup. Android would need its own route (App Actions).
